# Live UART: face feature and codec mapping — 2026-11-04

UART CH340 115200 8N1 is receiving Pi output and accepts commands. ESP32 held
in reset to avoid driving the shared receive net. Evidence is retained in
work/pi-uart-live-20261104.log (user requested clearing it once).

## Runtime observations

- Interactive console is UID/GID 2000, u:r:shell:s0; not root.
- sys.boot_completed is unset during the observed UI hang.
- portssh is running; /data/local/tmp/portssh.log records it listening on
  PI_IP:2222. `ip -4 addr` shows only loopback, explaining unreachable SSH.
- A system_server thread repeatedly waits for
  android.hardware.biometrics.face.virtualhal.IVirtualHal/virtual. `pm list
  features` confirms android.hardware.biometrics.face; no face binary is present
  in system_ext/bin/hw. Reference FaceService.getDeclaredInstances unconditionally
  adds virtual; FaceSensorConfigurations maps its IFace lookup to IVirtualHal.
  SystemServer starts FaceService only when the face feature is advertised.
  The Pi has no such face sensor. This is a demonstrably incorrect feature
  declaration; whether it accounts for every Launcher hang remains to be tested.
- FFmpeg codec2 attempts to register
  android.hardware.media.c2.IComponentStore/ffmpeg as mediacodec and is denied
  against default_android_service. The system service_contexts lacks this name;
  existing policy grants mediacodec (via hal_codec2_server) add on hal_codec2_service.

## Diagnostic noise and repairs

The old state collector's service list enumerates protected HALs and produces
shell find/call denials. Its getprop apexd.status also lacks permission. Stopped
that shell-owned collector (PID 525) during this boot, without stopping system
services. Replaced service list in source with service check for appwidget/wifi,
and removed the protected property query.

Persistent logcat still did not start: UART has init denied getattr on
/system/bin/logcat (logcat_exec). This was distinct from the earlier directory
creation failure. The source rc now launches /system/bin/sh with explicit shell
domain, then execs logcat, using the existing shell execute_no_trans permission.
No new policy allows are required. During this boot logcat was successfully
started directly from console shell into /data/local/tmp/uart-logcat.txt with
rotation (4 MiB, two archives).

## Live boot after laptop restart — 2026-11-04

The physical SSD booted with the M7 changes. On this boot the board initially
selected HSUM system user 0, while desktop user 10 remained stopped and
`sys.boot_completed` was blank. Runtime `am switch-user 10` brought boot to
complete. The UART and SSH shell then agreed on current user 10, user 10
running, Launcher focused, and no post-boot ANR. Rechecking after about 20
seconds showed the same Launcher process. Face HAL wait and FFmpeg
service-registration denial were absent in the live boot log. The automatic
boot-user selection still needs a deliberate fix before claiming direct
boot-to-desktop behavior.

Chrome was launched through ActivityManager for reproduction. First launch
native-aborted after ANGLE/Mesa failed GLES 3.0 `eglCreateContext` with
`EGL_BAD_ATTRIBUTE`, despite SurfaceFlinger reporting V3D 7.1 and ES 3.1.
Chromium then reported that its GPU process was unusable. A temporary
`--disable-gpu` command-line experiment instead hit an Android linker
reservation failure loading Trichrome (`7,991,296` bytes available versus
`209,317,888` requested); the command-line file was cleared afterward. Chrome
remains unresolved. Separately, Google Search startup processes and Play Store
hit early startup ANRs; they were not observed recurring during the short
post-switch Launcher check. `gscd` still aborts every few seconds because the
Pi has no `/dev/tpm0`.

Chrome startup follow-up: the persistent OpenGL ES ANGLE choice now survives
a cold app restart without debug settings and uses Mesa V3D acceleration. See
[chrome_angle_gles_fix.md](chrome_angle_gles_fix.md) for evidence, bootstrap
steps, limits and correction of the earlier linker-reservation hypothesis.
